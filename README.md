# db_bloat

A small PostgreSQL toolkit to build a lab database full of **table and index
bloat**, with a **different amount of bloat in each table**. Use it to
practice monitoring and cleanup with `VACUUM`, `REINDEX`, `pg_repack` and
friends.

> **Lab use only.** The scripts generate a lot of data and WAL. Never run
> them against a production database.

## How it works

| Object | Type | Role |
| --- | --- | --- |
| `sp_create_populated_tables` | procedure | Creates N tables and loads M rows into each one. |
| `sp_generate_bloat` | procedure | Disables autovacuum on those tables and runs random `UPDATE`s so each table ends up with a different share of dead tuples. |
| `bloat_plan` | table | Records the target of each table so you can compare it with what is actually measured. |

### The bloat method

- Tables are ordered by `md5(table name)` and the dead-tuple targets are
  spread linearly over a range (default **5% to 45%**). Every table gets a
  distinct target, and the order is shuffled relative to the table names.
- To reach a dead-tuple share `t`, a fraction `t / (1 - t)` of the rows is
  updated, because each updated row leaves one dead version behind. For
  example, 45% dead tuples means updating about 82% of the rows.
- Rows are picked with `random()`, so dead tuples are spread across all
  pages.
- The `UPDATE` changes `created_at`, an **indexed** column. This prevents
  HOT updates, so the indexes bloat along with the tables.
- Autovacuum is turned off on every target table, otherwise it would clean
  up the dead tuples right away.

## Requirements

- PostgreSQL 11 or later (procedures that `COMMIT` inside).
- No extensions. The verification and ranking queries use only the system
  catalogs and statistics views, so any role that can read the tables is
  enough.
- Disk space, roughly:
  - ~150 MB per table with 1M rows (data plus 3 indexes), so ~15 GB for the
    default 100 tables.
  - A few extra GB for the dead tuples, plus the WAL generated by the
    updates. Check `max_wal_size` and free disk before running.

## Quick start

```bash
git clone https://github.com/juliano777/db_bloat.git
cd db_bloat
psql -f db_bloat.sql
```

`db_bloat.sql` creates the `db_bloat` database, connects to it
(`\c db_bloat`), and creates `bloat_plan` and both procedures, so run it
with `psql`.

Then, connected to `db_bloat`:

```sql
\timing on

-- 1. Create and populate the tables (outside a BEGIN block)
CALL sp_create_populated_tables();      -- 100 tables x 1,000,000 rows
ANALYZE;

-- 2. Generate bloat
CALL sp_generate_bloat();               -- range 0.05 to 0.45
```

Try a small run first:

```sql
CALL sp_create_populated_tables(3, 1000);
CALL sp_generate_bloat();
```

## Procedures

### `sp_create_populated_tables`

```sql
CALL sp_create_populated_tables(p_tables, p_rows, p_table_base_name);
```

| Parameter | Default | Description |
| --- | --- | --- |
| `p_tables` | `100` | Number of tables to create. |
| `p_rows` | `1000000` | Rows loaded into each table. |
| `p_table_base_name` | `'tb_bloat_'` | Table name prefix. Tables are named `<prefix>001`, `<prefix>002`, and so on. |

Each table has the columns `id`, `customer_id`, `amount`, `status`,
`created_at` and `payload`, a primary key on `id`, and indexes on
`customer_id` and `created_at`. Existing tables with the same names are
**dropped and recreated**.

### `sp_generate_bloat`

```sql
CALL sp_generate_bloat(p_min_ratio, p_max_ratio, p_table_base_name);
```

| Parameter | Default | Description |
| --- | --- | --- |
| `p_min_ratio` | `0.05` | Lowest dead-tuple share (5%). |
| `p_max_ratio` | `0.45` | Highest dead-tuple share (45%). |
| `p_table_base_name` | `'tb_bloat_'` | Prefix of the tables to process. |

The range must satisfy `0 < min <= max < 1`. Examples:

```sql
CALL sp_generate_bloat(0.10, 0.30);              -- custom range
CALL sp_generate_bloat(0.05, 0.45, 'tb_test_');  -- custom prefix
```

Notes:

- Each call **adds** bloat to what already exists. To start over, recreate
  the tables with `sp_create_populated_tables`.
- Avoid heavy `SELECT`s and `VACUUM` on these tables before measuring,
  because page pruning can remove part of the dead tuples.
- Both procedures commit once per table, so call them outside an explicit
  transaction block.

## Verify the result

Compare the target of each table with the share of dead tuples that
PostgreSQL itself counts. No extension is needed:

```sql
SELECT p.table_name,
       p.target_ratio,
       round(s.n_dead_tup::numeric
             / nullif(s.n_live_tup + s.n_dead_tup, 0), 4)
                                       AS actual_dead_ratio,
       s.n_live_tup,
       s.n_dead_tup
FROM bloat_plan p
JOIN pg_stat_user_tables s ON s.schemaname = 'public'
                          AND s.relname = p.table_name
ORDER BY p.target_ratio;
```

The counters come from the statistics system and count tuples, so
`actual_dead_ratio` should land very close to `target_ratio`. They are
updated asynchronously, so wait a few seconds after the `CALL`. A statistics
reset or a crash zeroes them.

For a quick overview of the tables with the most dead tuples:

```sql
SELECT relname, n_live_tup, n_dead_tup
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 15;
```

## Finding the most bloated objects

The two queries below rank tables and indexes by **estimated** bloat in
bytes. They use only the system catalogs and the planner statistics, so no
extension is required. Both use CTEs instead of subqueries, return every
size in **bytes** (no "pretty" formatting) and sort by `bloat_size` and then
`total_size`, both descending. Add a `LIMIT` to see only the top of the
list.

How the estimate works: from the live row count (`reltuples`) and the
average column widths in `pg_stats`, the queries work out how many pages the
relation would need if it had no bloat, and call everything beyond that
bloat. Therefore:

- Run `ANALYZE` first. Relations that have not been analyzed are skipped.
- `pg_stats` only shows columns the current role can read.
- It is an estimate. It ignores column alignment padding, so a freshly
  loaded table can show a few percent of bloat. In tests it ranked the
  tables in the same order as exact measurements.

### Most bloated tables

```sql
WITH settings AS (
    SELECT current_setting('block_size')::int AS block_size,
           24                                 AS page_header,
           8                                  AS max_align
),
table_columns AS (
    SELECT s.schemaname,
           s.tablename,
           count(*)                                      AS ncols,
           sum((1 - s.null_frac::float8) * s.avg_width)  AS data_width,
           max(s.null_frac)                              AS max_null_frac
    FROM pg_stats s
    WHERE NOT s.inherited
    GROUP BY s.schemaname, s.tablename
),
tables AS (
    SELECT n.nspname                AS schema_name,
           c.relname                AS table_name,
           c.reltuples,
           pg_relation_size(c.oid)  AS total_size,
           COALESCE(substring(array_to_string(c.reloptions, ',')
                              FROM 'fillfactor=(\d+)')::int, 100)
                                    AS fillfactor,
           tc.ncols,
           tc.data_width,
           tc.max_null_frac
    FROM pg_class c
    JOIN pg_namespace n   ON n.oid = c.relnamespace
    JOIN table_columns tc ON tc.schemaname = n.nspname
                         AND tc.tablename = c.relname
    WHERE c.relkind IN ('r', 'm')
      AND c.relpersistence <> 't'
      AND c.reltuples > 0
      AND n.nspname NOT IN ('pg_catalog', 'information_schema')
      AND n.nspname !~ '^pg_toast'
),
estimates AS (
    SELECT t.schema_name,
           t.table_name,
           t.total_size,
           st.block_size,
           ceil(t.reltuples / floor(
               (st.block_size - st.page_header) * t.fillfactor / 100.0
               / (4
                  + ceil((23 + CASE WHEN t.max_null_frac > 0
                                    THEN ceil(t.ncols / 8.0) ELSE 0 END)
                         / st.max_align) * st.max_align
                  + ceil(t.data_width / st.max_align) * st.max_align)
           )) AS expected_pages
    FROM tables t
    CROSS JOIN settings st
)
SELECT schema_name,
       table_name,
       total_size,
       (greatest(0, total_size / block_size - expected_pages)
        * block_size)::bigint AS bloat_size
FROM estimates
ORDER BY bloat_size DESC, total_size DESC;
```

- `total_size` is the size of the table's main fork. Indexes and TOAST are
  not included.
- `bloat_size` is the space occupied by pages beyond the expected number.
  The expected size counts, per row, the 4-byte line pointer, the tuple
  header (23 bytes plus a null bitmap when the table has nullable data),
  the column data, 8-byte alignment, and the table fillfactor.
- Partitioned parents are not listed, but their partitions are.

### Most bloated indexes

```sql
WITH settings AS (
    SELECT current_setting('block_size')::int AS block_size,
           24                                 AS page_header,
           16                                 AS special_space,
           8                                  AS max_align
),
indexes AS (
    SELECT n.nspname                  AS schema_name,
           t.relname                  AS table_name,
           ic.relname                 AS index_name,
           ic.reltuples,
           pg_relation_size(ic.oid)   AS total_size,
           COALESCE(substring(array_to_string(ic.reloptions, ',')
                              FROM 'fillfactor=(\d+)')::int, 90)
                                      AS fillfactor,
           count(*)                   AS ncols,
           sum((1 - COALESCE(s.null_frac, 0)::float8)
               * COALESCE(s.avg_width, 0))
                                      AS data_width,
           max(s.null_frac)           AS max_null_frac
    FROM pg_index i
    JOIN pg_class ic     ON ic.oid = i.indexrelid
    JOIN pg_class t      ON t.oid = i.indrelid
    JOIN pg_namespace n  ON n.oid = t.relnamespace
    JOIN pg_am am        ON am.oid = ic.relam
    JOIN pg_attribute a  ON a.attrelid = ic.oid AND a.attnum > 0
    LEFT JOIN pg_stats s ON s.schemaname = n.nspname
                        AND s.attname = a.attname
                        AND NOT s.inherited
                        AND s.tablename = CASE WHEN i.indkey[a.attnum - 1] > 0
                                               THEN t.relname
                                               ELSE ic.relname END
    WHERE am.amname = 'btree'
      AND ic.relkind = 'i'
      AND ic.relpersistence <> 't'
      AND i.indisvalid
      AND ic.reltuples > 0
      AND n.nspname NOT IN ('pg_catalog', 'information_schema')
      AND n.nspname !~ '^pg_toast'
    GROUP BY n.nspname, t.relname, ic.relname, ic.oid,
             ic.reltuples, ic.reloptions
    HAVING count(s.attname) = count(*)
),
estimates AS (
    SELECT x.schema_name,
           x.table_name,
           x.index_name,
           x.total_size,
           st.block_size,
           1 + ceil(x.reltuples / floor(
               (st.block_size - st.page_header - st.special_space)
               * x.fillfactor / 100.0
               / (4
                  + ceil((8 + CASE WHEN x.max_null_frac > 0
                                   THEN ceil(x.ncols / 8.0) ELSE 0 END)
                         / st.max_align) * st.max_align
                  + ceil(x.data_width / st.max_align) * st.max_align)
           )) AS expected_pages
    FROM indexes x
    CROSS JOIN settings st
)
SELECT schema_name,
       table_name,
       index_name,
       total_size,
       (greatest(0, total_size / block_size - expected_pages)
        * block_size)::bigint AS bloat_size
FROM estimates
ORDER BY bloat_size DESC, total_size DESC;
```

- Only B-tree indexes are listed. Invalid and temporary indexes are
  skipped, and so are indexes with a column that has no statistics yet.
- `total_size` is the size of the index.
- `bloat_size` is the space occupied by pages beyond the expected number
  for a freshly built index with the same entries. The expected size counts
  the metapage, the 4-byte line pointer, the 8-byte index tuple header, the
  column data, 8-byte alignment, and the index fillfactor (default 90).
  Columns of expression indexes use the statistics stored under the index
  name.
- The upper levels of the B-tree (about 1% of the index) are not counted,
  so the estimate can be slightly high.

## Cleaning up the bloat

Practice removing the bloat and compare the sizes before and after:

```sql
-- frees dead tuples, but the file does not shrink
VACUUM VERBOSE tb_bloat_001;

-- rebuilds the indexes (PostgreSQL 12+)
REINDEX TABLE CONCURRENTLY tb_bloat_001;

-- rewrites the table (exclusive lock)
VACUUM FULL tb_bloat_001;
```

Or use [`pg_repack`](https://github.com/reorg/pg_repack) to rewrite tables
and indexes without a long lock.

To turn autovacuum back on for a table:

```sql
ALTER TABLE tb_bloat_001 RESET (autovacuum_enabled);
```

To remove everything and free the disk space:

```sql
DROP DATABASE db_bloat;
```
