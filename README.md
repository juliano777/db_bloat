# db_bloat

A small PostgreSQL toolkit to build a lab database full of **table and index
bloat**, with a **different amount of bloat in each table**. Use it to
practice monitoring and cleanup with `pgstattuple`, `VACUUM`, `REINDEX`,
`pg_repack` and friends.

> **Lab use only.** The scripts generate a lot of data and WAL. Never run
> them against a production database.

## How it works

| Object | Type | Role |
| --- | --- | --- |
| `sp_create_populated_tables` | procedure | Creates N tables and loads M rows into each one. |
| `sp_generate_bloat` | procedure | Disables autovacuum on those tables and runs random `UPDATE`s so each table ends up with a different share of dead tuples. |
| `bloat_plan` | table | Records the target of each table so you can compare it with what is actually measured. |

### The bloat method

- Tables are ordered by `md5(table name)` and the dead-tuple targets are
  spread linearly over a range (default **5% to 45%**). Every table gets a
  distinct target, and the order is shuffled relative to the table names.
- To reach a dead-tuple share `t`, a fraction `t / (1 - t)` of the rows is
  updated, because each updated row leaves one dead version behind. For
  example, 45% dead tuples means updating about 82% of the rows.
- Rows are picked with `random()`, so dead tuples are spread across all
  pages.
- The `UPDATE` changes `created_at`, an **indexed** column. This prevents
  HOT updates, so the indexes bloat along with the tables.
- Autovacuum is turned off on every target table, otherwise it would clean
  up the dead tuples right away.

## Requirements

- PostgreSQL 11 or later (procedures that `COMMIT` inside).
- The `pgstattuple` extension (part of `contrib`) for the verification
  step. Creating it normally requires superuser privileges.
- Disk space, roughly:
  - ~150 MB per table with 1M rows (data plus 3 indexes), so ~15 GB for the
    default 100 tables.
  - A few extra GB for the dead tuples, plus the WAL generated by the
    updates. Check `max_wal_size` and free disk before running.

## Quick start

```bash
git clone https://github.com/juliano777/db_bloat.git
cd db_bloat
psql -f db_bloat.sql
```

`db_bloat.sql` creates the `db_bloat` database, connects to it
(`\c db_bloat`), and creates `bloat_plan` and both procedures, so run it
with `psql`.

Then, connected to `db_bloat`:

```sql
\timing on

-- 1. Create and populate the tables (outside a BEGIN block)
CALL sp_create_populated_tables();      -- 100 tables x 1,000,000 rows
ANALYZE;

-- 2. Generate bloat
CALL sp_generate_bloat();               -- range 0.05 to 0.45
```

Try a small run first:

```sql
CALL sp_create_populated_tables(3, 1000);
CALL sp_generate_bloat();
```

## Procedures

### `sp_create_populated_tables`

```sql
CALL sp_create_populated_tables(p_tables, p_rows, p_table_base_name);
```

| Parameter | Default | Description |
| --- | --- | --- |
| `p_tables` | `100` | Number of tables to create. |
| `p_rows` | `1000000` | Rows loaded into each table. |
| `p_table_base_name` | `'tb_bloat_'` | Table name prefix. Tables are named `<prefix>001`, `<prefix>002`, and so on. |

Each table has the columns `id`, `customer_id`, `amount`, `status`,
`created_at` and `payload`, a primary key on `id`, and indexes on
`customer_id` and `created_at`. Existing tables with the same names are
**dropped and recreated**.

### `sp_generate_bloat`

```sql
CALL sp_generate_bloat(p_min_ratio, p_max_ratio, p_table_base_name);
```

| Parameter | Default | Description |
| --- | --- | --- |
| `p_min_ratio` | `0.05` | Lowest dead-tuple share (5%). |
| `p_max_ratio` | `0.45` | Highest dead-tuple share (45%). |
| `p_table_base_name` | `'tb_bloat_'` | Prefix of the tables to process. |

The range must satisfy `0 < min <= max < 1`. Examples:

```sql
CALL sp_generate_bloat(0.10, 0.30);              -- custom range
CALL sp_generate_bloat(0.05, 0.45, 'tb_test_');  -- custom prefix
```

Notes:

- Each call **adds** bloat to what already exists. To start over, recreate
  the tables with `sp_create_populated_tables`.
- Avoid heavy `SELECT`s and `VACUUM` on these tables before measuring,
  because page pruning can remove part of the dead tuples.
- Both procedures commit once per table, so call them outside an explicit
  transaction block.

## Verify the result

```sql
CREATE EXTENSION IF NOT EXISTS pgstattuple;

SELECT p.table_name,
       p.target_ratio,
       round((s.dead_tuple_percent / 100)::numeric, 4) AS actual_dead_ratio,
       round((s.free_percent / 100)::numeric, 4)       AS free_ratio,
       pg_size_pretty(s.table_len)                     AS table_size
FROM bloat_plan p
CROSS JOIN LATERAL
     pgstattuple(('public.' || quote_ident(p.table_name))::regclass) s
ORDER BY p.target_ratio;
```

`pgstattuple` computes percentages over table bytes, so `actual_dead_ratio`
usually lands a little below the target while keeping the same ordering and
spread. This query reads every table in full, so it takes a while with 100
tables. Limit it with a `WHERE` clause for a quick check.

To inspect index bloat, look at one index at a time. A low
`avg_leaf_density` means a bloated index:

```sql
SELECT * FROM pgstatindex('tb_bloat_001_customer_id_idx');
```

For a quick overview from the statistics views:

```sql
SELECT relname, n_live_tup, n_dead_tup
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 15;
```

## Finding the most bloated objects

The two queries below rank tables and indexes by bloat. Both use CTEs
instead of subqueries, return every size in **bytes** (no "pretty"
formatting) and sort by `bloat_size` and then `total_size`, both
descending. Add a `LIMIT` to see only the top of the list.

They need the `pgstattuple` extension and a role allowed to use it (a
superuser or a member of `pg_stat_scan_tables`).

### Most bloated tables

```sql
WITH tables AS (
    SELECT c.oid        AS table_oid,
           n.nspname    AS schema_name,
           c.relname    AS table_name
    FROM pg_class c
    JOIN pg_namespace n ON n.oid = c.relnamespace
    WHERE c.relkind IN ('r', 'm')
      AND c.relpersistence <> 't'
      AND n.nspname NOT IN ('pg_catalog', 'information_schema')
      AND n.nspname !~ '^pg_toast'
),
stats AS (
    SELECT t.schema_name,
           t.table_name,
           s.table_len                               AS total_size,
           s.dead_tuple_len + s.approx_free_space    AS bloat_size
    FROM tables t
    CROSS JOIN LATERAL pgstattuple_approx(t.table_oid) s
)
SELECT schema_name, table_name, total_size, bloat_size
FROM stats
ORDER BY bloat_size DESC, total_size DESC;
```

- `total_size` is the size of the table's main fork. Indexes and TOAST are
  not included.
- `bloat_size` is the space taken by dead tuples plus the free space inside
  the pages, as reported by `pgstattuple_approx`.
- `pgstattuple_approx` skips pages that are all-visible, so it is much
  faster than `pgstattuple` and still accurate here, because the pages with
  dead tuples are not all-visible. For exact numbers, call
  `pgstattuple(t.table_oid)` and use `s.free_space` instead of
  `s.approx_free_space`.
- Partitioned parents are not listed, but their partitions are.

### Most bloated indexes

```sql
WITH indexes AS (
    SELECT ic.oid       AS index_oid,
           n.nspname    AS schema_name,
           t.relname    AS table_name,
           ic.relname   AS index_name,
           COALESCE(substring(array_to_string(ic.reloptions, ',')
                              FROM 'fillfactor=(\d+)')::float8, 90)
                        AS fillfactor
    FROM pg_index i
    JOIN pg_class ic    ON ic.oid = i.indexrelid
    JOIN pg_class t     ON t.oid = i.indrelid
    JOIN pg_namespace n ON n.oid = t.relnamespace
    JOIN pg_am am       ON am.oid = ic.relam
    WHERE am.amname = 'btree'
      AND ic.relkind = 'i'
      AND ic.relpersistence <> 't'
      AND i.indisvalid
      AND n.nspname NOT IN ('pg_catalog', 'information_schema')
      AND n.nspname !~ '^pg_toast'
),
stats AS (
    SELECT x.schema_name,
           x.table_name,
           x.index_name,
           s.index_size AS total_size,
           COALESCE(NULLIF(s.avg_leaf_density, 'NaN'), x.fillfactor)
                        AS leaf_density,
           x.fillfactor
    FROM indexes x
    CROSS JOIN LATERAL pgstatindex(x.index_oid) s
)
SELECT schema_name,
       table_name,
       index_name,
       total_size,
       round(total_size * greatest(0, 1 - leaf_density / fillfactor))::bigint
           AS bloat_size
FROM stats
ORDER BY bloat_size DESC, total_size DESC;
```

- Only B-tree indexes are listed, because `pgstatindex` supports only
  those. Invalid and temporary indexes are skipped.
- `total_size` is the size of the index.
- `bloat_size` is an **estimate**: the share of the index that is empty
  beyond its fillfactor, calculated as
  `index_size * (1 - avg_leaf_density / fillfactor)`, never below zero.
  The fillfactor comes from the index options and defaults to 90, so a
  freshly built index shows no bloat.
- Empty indexes have no leaf density (`NaN`) and are counted as having no
  bloat.

## Cleaning up the bloat

Practice removing the bloat and compare the sizes before and after:

```sql
-- frees dead tuples, but the file does not shrink
VACUUM VERBOSE tb_bloat_001;

-- rebuilds the indexes (PostgreSQL 12+)
REINDEX TABLE CONCURRENTLY tb_bloat_001;

-- rewrites the table (exclusive lock)
VACUUM FULL tb_bloat_001;
```

Or use [`pg_repack`](https://github.com/reorg/pg_repack) to rewrite tables
and indexes without a long lock.

To turn autovacuum back on for a table:

```sql
ALTER TABLE tb_bloat_001 RESET (autovacuum_enabled);
```

To remove everything and free the disk space:

```sql
DROP DATABASE db_bloat;
```
